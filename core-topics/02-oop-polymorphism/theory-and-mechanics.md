# Object-Oriented Programming & Polymorphism — Deep Theory & Mechanics

An exhaustive, low-level systems and compiler guide to C++ object models, single/multiple/virtual inheritance memory layouts, VTable and VPtr placement, thunk adjustment, dynamic dispatch mechanics, static polymorphism (CRTP), and devirtualization optimizations.

---

## 1. Object Models & Inheritance Memory Layout

### 1.1 Single Inheritance with Virtual Functions

When a class defines or inherits at least one `virtual` function, the compiler inserts an implicit pointer (`__vptr`) into the object instance pointing to the class's **Virtual Table (VTable)** in the `.rodata` section.

```
Class Base { int b; virtual void f(); };
Class Derived : public Base { int d; void f() override; virtual void g(); };

Derived Object Memory Layout (16 Bytes on x86-64):
+------------------------------------+ 0x00
| __vptr (8 Bytes)                   | ----------> VTable for Derived (.rodata)
+------------------------------------+ 0x08        +------------------------------+
| int b (4 Bytes)                    |             | offset-to-top: 0             |
+------------------------------------+ 0x0C        | RTTI typeinfo for Derived    |
| int d (4 Bytes)                    |             | &Derived::f()                |
+------------------------------------+ 0x10        | &Derived::g()                |
                                                   +------------------------------+
```

#### Detailed Breakdown of Virtual Functions & Virtual Pointers:

#### 1. What is a Virtual Function?
- **Static Binding (Early Binding / Non-Virtual Functions)**: 
  - Standard member functions are resolved entirely at **compile-time** based on the static compile-time type of the pointer or reference.
  - The compiler emits a direct `call FunctionAddress` instruction. There is zero runtime lookup overhead, but no polymorphism is possible.
- **Dynamic Binding (Late Binding / Virtual Functions)**:
  - Declaring a member function with the `virtual` keyword instructs the compiler to defer function resolution to **runtime**.
  - When invoked through a base pointer or reference (e.g. `Base* ptr = new Derived(); ptr->f();`), the program looks up the actual concrete object type at runtime and executes the most-derived override (`Derived::f()`).

---

#### 2. What is the Virtual Table Pointer (`__vptr`)?
- **Internal Structure**: An implicit, hidden 64-bit pointer (8 bytes on 64-bit platforms) inserted by the compiler into any class that declares or inherits at least one `virtual` function.
- **Placement**: Under the standard Itanium C++ ABI (used by GCC, Clang, and modern compilers on Linux/macOS), the `__vptr` is placed at **offset `0x00`** (the very beginning) of the object instance.
- **Initialization Lifecycle**:
  - The `__vptr` is **not** initialized by `malloc` or memory allocation.
  - It is initialized dynamically by the class's **constructor**.
  - During `Base::Base()`, the `__vptr` points to `Base::VTable`. When execution enters `Derived::Derived()`, the compiler updates the `__vptr` to point to `Derived::VTable`.
- **Memory Footprint Cost**: Every instance of a polymorphic class carries an 8-byte overhead for the `__vptr`, plus any additional alignment padding required by the CPU architecture.

---

#### 3. What is the Virtual Table (VTable)?
- **Location**: Generated by the compiler at compile-time as a `const` static array of function pointers stored in the **`.rodata` (Read-Only Data)** section of the executable binary.
- **Per-Class Instance**: There is **exactly ONE VTable per polymorphic class** (shared by all instances of that class across the entire process), NOT one per object instance.
- **Anatomy of a VTable Entry**:
  1. **Offset-to-Top**: A 64-bit signed integer storing the byte offset from the subobject `__vptr` to the beginning of the complete object (used for pointer adjustments in multiple inheritance; `0` in single inheritance).
  2. **RTTI Type Descriptor Pointer**: Points to the `std::type_info` descriptor for the class (used by `typeid` and `dynamic_cast`).
  3. **Array of Function Pointers**: An ordered table of code addresses pointing to the member function implementations (`&Derived::f()`, `&Derived::g()`).

---

#### 4. Step-by-Step Dynamic Dispatch Mechanics (Assembly Translation)
When your C++ code executes a polymorphic call:

```cpp
Base* p = new Derived();
p->f(); // Calls Derived::f()
```

The CPU executes the following steps under the hood:

```
[ Step 1: Load __vptr ]      mov rax, QWORD PTR [rdi]       ; Read __vptr from object (*p at offset 0)
[ Step 2: Index VTable ]     mov rax, QWORD PTR [rax + 16]  ; Load function address for f() (index 0)
[ Step 3: Indirect Jump ]    call rax                       ; Jump to Derived::f() with %rdi = this
```

1. **Fetch Object Pointer**: The base pointer `p` holds the object's starting address (`%rdi`).
2. **Fetch VTable Address**: The CPU dereferences `p` (`offset 0x00`) to read the 8-byte `__vptr` into a register.
3. **Fetch Function Address**: The CPU adds the known compile-time slot offset for `f()` to the VTable pointer and loads the concrete function pointer (`&Derived::f()`).
4. **Indirect Call**: The CPU executes an indirect call instruction (`call %rax`), passing `p` as the implicit `this` pointer in register `%rdi`.

### 1.2 Multiple Inheritance & Multiple VPtrs

In multiple inheritance, a derived class inherits from two or more independent base classes. Because each base class has its own memory layout and virtual functions, the derived class must maintain **multiple distinct subobjects**, resulting in **multiple VPtrs** and **Thunk pointer adjustments**.

```
Class Base1 { int b1; virtual void f1(); };
Class Base2 { int b2; virtual void f2(); };
Class MultiDerived : public Base1, public Base2 { int d; void f1() override; void f2() override; };

MultiDerived Object Memory Layout (32 Bytes on x86-64):
+------------------------------------+ 0x00  <-- MultiDerived* md & Base1* b1 point here
| Base1::__vptr (8 Bytes)            | ----------> Primary VTable (for MultiDerived / Base1)
+------------------------------------+ 0x08        +---------------------------------------+
| int b1 (4 Bytes)                   |             | offset-to-top: 0                      |
| [Padding: 4 Bytes]                 |             | RTTI for MultiDerived                 |
+------------------------------------+ 0x10  <--   | &MultiDerived::f1()                   |
| Base2::__vptr (8 Bytes)            | ----+       +---------------------------------------+
+------------------------------------+ 0x18|
| int b2 (4 Bytes)                   |     +-----> Secondary VTable (for Base2 in MultiDerived)
| int d  (4 Bytes)                   |             +---------------------------------------+
+------------------------------------+ 0x20        | offset-to-top: -16                    |
                                                   | RTTI for MultiDerived                 |
                                                   | &non-virtual thunk to MultiDerived::f2|
                                                   +---------------------------------------+
```

---

#### 1. Why Does Multiple Inheritance Require Multiple VPtrs?
1. **Physical Memory Layout Constraint**:
   - `MultiDerived` contains a complete `Base1` subobject and a complete `Base2` subobject.
   - `Base1` is placed at offset `0x00`. When you cast `MultiDerived* md` to `Base1* b1 = md;`, `b1` points to memory address `0x00`.
   - `Base2` cannot also be at `0x00` (otherwise its members would overwrite `Base1`'s data!). It is placed at **offset `0x10` (+16 bytes)**.
2. **Independent Polymorphic Interfaces**:
   - When a caller has a `Base2* b2` pointer, the caller might not even know that the object is actually a `MultiDerived` instance!
   - The caller expects to find a VPtr at `b2`'s address (`*(b2)` at offset `0x10`).
   - Therefore, `Base2` **must have its own secondary `__vptr` located at offset `0x10`** pointing to a secondary VTable.

---

#### 2. The "Pointer Offset Mismatch" Problem
Consider what happens when you invoke a virtual function through the secondary base pointer:

```cpp
MultiDerived* md = new MultiDerived();
Base2* b2 = md; // Implicit pointer adjustment! b2 = (char*)md + 16
b2->f2();       // Calling virtual function via secondary base pointer
```

- **The Caller's State**:
  - The caller holds `b2` (which points to address `0x10`).
  - To call `f2()`, the caller loads `Base2`'s VTable from `*(b2)` and passes `b2` (address `0x10`) in the `%rdi` register as the implicit `this` pointer (System V AMD64 ABI).
- **The Callee's Expectation**:
  - `MultiDerived::f2()` is a member function of `MultiDerived`.
  - Inside `MultiDerived::f2()`, code accesses members like `this->d` (at offset `0x1C` relative to the *start* of `MultiDerived`) and `this->b1` (at offset `0x08`).
  - `MultiDerived::f2()` expects the `%rdi` register (`this`) to point to the **start of `MultiDerived` (address `0x00`)**, NOT `0x10`!
- **The Conflict**: If `MultiDerived::f2()` ran directly with `this = 0x10`, accessing `this->b1` (offset `+0x08`) would read `b2`'s padding, causing memory corruption!

---

#### 3. What is a Thunk?
A **Thunk** (also called an *adjustment thunk* or *trampoline*) is a tiny, compiler-generated assembly shim function whose sole purpose is to **adjust the `this` pointer (`%rdi`) before jumping to the actual member function**.

Instead of placing `&MultiDerived::f2()` directly inside `Base2`'s secondary VTable, the compiler places a pointer to the **Thunk**:

```assembly
# Compiler-generated Non-Virtual Thunk in assembly:
__non_virtual_thunk_to_MultiDerived::f2():
    sub rdi, 16                 # 1. Adjust `this` pointer: subtract 16 to move from Base2 (0x10) to MultiDerived (0x00)
    jmp MultiDerived::f2()      # 2. Tail-call jump directly to the real member function!
```

---

#### 4. Step-by-Step Execution Walkthrough of a Thunk Call:

```
[ Caller: b2->f2() ]
       |
       | 1. Dereferences `b2` (at 0x10) to fetch Base2::__vptr
       | 2. Loads function pointer from Secondary VTable slot
       | 3. Passes %rdi = 0x10 and calls function pointer
       v
[ Assembly Thunk: `__non_virtual_thunk_to_MultiDerived::f2()` ]
       |
       | 4. Executes `sub rdi, 16` -> %rdi is now 0x00 (True start of MultiDerived!)
       | 5. Executes `jmp MultiDerived::f2()`
       v
[ Real Function: `MultiDerived::f2()` ]
       |
       | 6. Executes with correct `this = 0x00`. Reads `this->b1` and `this->d` safely!
       v
[ Normal Return back to Caller ]
```

---

#### 5. Non-Virtual Thunk vs. Virtual Thunk
- **Non-Virtual Thunk**: Used in standard multiple inheritance where the offset between the base subobject and the complete object is **constant and fixed at compile-time** (e.g. constant `-16`). The adjustment `sub rdi, 16` is hardcoded as a single instruction.
- **Virtual Thunk**: Used in **Virtual Inheritance** where the offset to the virtual base subobject varies dynamically at runtime depending on what class is the most-derived object. A virtual thunk dynamically reads the offset from a `vcall-offset` entry in the VTable before adjusting `%rdi`.

### 1.3 The Diamond Problem & Virtual Inheritance

Without `virtual` base inheritance, inheriting from two classes that share a common ancestor creates duplicate ancestor subobjects, causing **ambiguity** and **memory bloat**.

```
Non-Virtual Diamond (Duplicate Base):          Virtual Inheritance (Shared Base):
             [ Base ]                                       [ Base ]
            /        \                                     //      \\
     [ Left ]        [ Right ]                     [ Left ]          [ Right ]
            \        /                                     \\      //
         [ Bottom ]                                         [ Bottom ]
  (Contains Base::Left and Base::Right)               (Contains exactly 1 Base)
```

#### Memory Layout with Virtual Inheritance:
The shared `Base` subobject is placed at the **very end** of the most derived class, and intermediate classes store virtual base pointers (`vptr` / `vbtable` / offset entries) to dynamically locate the shared `Base` at runtime.

## 2. Virtual Function Call Mechanics & Dynamic Dispatch

### 2.1 Assembly Mechanics & Instruction Flow

When your C++ code invokes a virtual function through a pointer or reference (`ptr->virtual_func(arg)`), the compiler cannot emit a direct `call FunctionAddress` instruction. Instead, it emits a sequence of **three low-level machine instructions** (System V AMD64 ABI):

```assembly
# Target: Calling ptr->virtual_func(42)
# Register state on entry: %rdi = ptr (object address), %esi = 42 (argument)

mov rax, QWORD PTR [rdi]        # 1. First Memory Load: Read `__vptr` from object instance at offset 0x00
mov rax, QWORD PTR [rax + 16]   # 2. Second Memory Load: Read function pointer from VTable at slot offset (+16)
call rax                        # 3. Indirect Call: Jump to function pointer stored in register %rax
```

In contrast, a **non-virtual** function call emits a single, immediate instruction:
```assembly
call Class::non_virtual_func    # Direct Call: Destination address is hardcoded into the binary opcode
```

---

### 2.2 The 3 Real-World Performance Overheads of Virtual Calls

While dynamic dispatch is foundational to object-oriented polymorphism, it imposes significant hardware microarchitecture penalties in high-performance and low-latency systems:

```
+-------------------------------------------------------------------------------+
| THE THREE PERFORMANCE TAXES OF VIRTUAL CALLS                                  |
|                                                                               |
|  1. Double Memory Indirection: 2 cache loads (Object -> VTable -> Code)       |
|  2. Branch Target Misprediction: BTB misses trigger 15-20 cycle CPU flushes   |
|  3. Compiler Inlining Barrier: Blocks constant folding, unrolling & SIMD      |
+-------------------------------------------------------------------------------+
```

#### Cost 1: Double Memory Indirection & Cache Footprint
- A direct call requires **0 memory loads** to find the function address (it is hardcoded directly in the CPU instruction stream).
- A virtual call requires **two sequential memory loads**:
  1. Load `__vptr` from the object memory (triggers an L1/L2 cache miss if the object is cold).
  2. Load the function pointer from the VTable in `.rodata` (triggers another cache miss if the VTable page is cold).
- If both loads miss CPU caches and hit main RAM, dispatch latency alone can consume **$\sim 100 - 200\text{ ns}$** before the function body even starts executing!

#### Cost 2: Indirect Branch Target Misprediction & CPU Pipeline Flushes
- Modern out-of-order CPUs use a specialized hardware table called the **Branch Target Buffer (BTB)** to predict the target address of indirect `call *%rax` instructions before the memory loads complete.
- **The Problem**: If a loop iterates through a polymorphic container (`std::vector<Base*>`) where object types alternate (e.g. `Circle` $\to$ `Square` $\to$ `Circle` $\to$ `Triangle`):
  - The BTB cannot predict which concrete function will be called next.
  - When the prediction is wrong, the CPU suffers a **Pipeline Flush penalty** of **15 to 20 clock cycles**, discarding all speculatively executed instructions and restarting the execution pipeline from scratch.

#### Cost 3: The Inlining Barrier (The "Mother of All Optimizations")
- **Inlining** replaces a function call with the actual body of the function, eliminating call/return register saves (`push %rbp`, `pop %rbp`, stack frame setup).
- More importantly, inlining enables secondary compiler optimizations:
  - Constant propagation and constant folding.
  - Dead code elimination across caller/callee boundaries.
  - Loop vectorization using AVX2/AVX-512 SIMD instructions.
- **The Penalty**: Because the compiler cannot know which override will be called at runtime, virtual calls **strictly prevent inlining**. For small functions (such as 1-line getters or mathematical vector operations), the call/return overhead is often **$10\times - 50\times$ more expensive** than the function body itself!

---

### 2.3 Devirtualization Optimizations

Modern C++ optimizing compilers (GCC, Clang, MSVC) employ four distinct strategies to prove the concrete type of an object at compile-time, turning indirect virtual calls back into fast, inlinable direct calls (**Devirtualization**):

#### 1. Direct Object / Local Type Knowledge
When an object is created locally on the stack or allocated with an exact concrete type, the compiler knows its exact dynamic type with 100% certainty:

```cpp
Derived d;
d.f(); // Devirtualized! Compiler knows 'd' is Derived -> Direct call to Derived::f()

auto p = std::make_unique<Derived>();
p->f(); // Devirtualized! make_unique returns unique_ptr<Derived>, so target is known!
```

#### 2. The `final` Specifier (Class & Method Devirtualization)
Marking a class or a virtual method as `final` informs the compiler that **no further derived classes can ever override this function**:

```cpp
class FastRenderer final : public IRenderer {
public:
    void render() override final { /* ... */ }
};

void draw(FastRenderer* r) {
    r->render(); // Devirtualized & INLINED! Compiler proves no subclasses exist to override render()!
}
```

#### 3. Speculative Devirtualization (Profile-Guided Optimization - PGO)
Under `-fprofile-generate` and `-fprofile-use`, the compiler analyzes runtime execution profiles. If a polymorphic call site executes `DerivedA::f()` 99% of the time, the compiler inserts a speculative fast-path check:

```cpp
// What the compiler emits internally during Speculative Devirtualization:
if (p->__vptr == &DerivedA::vtable) {
    DerivedA::f_inlined(p); // Fast Path: Inlined with ZERO virtual call overhead!
} else {
    p->f();                 // Slow Path: Fallback to indirect VTable call
}
```

#### 4. Whole-Program Devirtualization via Link-Time Optimization (LTO / `-flto`)
- During standard compilation, each `.cpp` translation unit is compiled in isolation. The compiler cannot devirtualize `Base* ptr->f()` because another `.cpp` file might define a hidden derived class.
- With **Link-Time Optimization (`-flto`)**, the linker analyzes the complete program call graph across all object files. If it proves that only **one derived class exists in the entire binary**, it strips the VTable lookup globally and rewrites the call to a direct function call!

## 3. Critical Traps & Anti-Patterns

### 3.1 Why Virtual Function Calls in Constructors/Destructors Do NOT Dispatch Dynamically

#### 1. The Core Object Lifetime Safety Principle
In C++, an object is constructed layer-by-layer from the base class down to the most-derived class (**Base-First Construction**), and destroyed in the exact reverse order (**Derived-First Destruction**):

```
CONSTRUCTION TIMELINE:
  [ 1. Allocate Raw Memory ] -> [ 2. Base::Base() ] ---------> [ 3. Derived::Derived() ]
                                 (Derived members NOT yet        (Derived members now fully
                                  initialized in memory!)         initialized & ready)

DESTRUCTION TIMELINE:
  [ 1. Derived::~Derived() ] -> [ 2. Base::~Base() ] ---------> [ 3. Free Raw Memory ]
  (Derived members torn down;    (Only Base subobject remains)
   Derived state no longer valid)
```

**Why Dynamic Dispatch to Derived is Dangerous**:
- During `Base::Base()`, the `Derived` class constructor has **not yet executed**. The derived class member variables (e.g. heap pointers, strings, file handles) are uninitialized garbage.
- If C++ allowed dynamic dispatch to `Derived::virtual_func()` from `Base::Base()`, the derived implementation would attempt to access uninitialized members, causing immediate **Undefined Behavior, memory corruption, and crashes**.
- Therefore, the ISO C++ Standard (§ [class.cdtor]) mandates: **During the execution of a constructor or destructor, the dynamic type of the object is that of the currently executing constructor/destructor class, NOT the most-derived class!**

---

#### 2. The Mechanics of `__vptr` Mutation Under the Hood
To enforce this guarantee at the hardware level, the compiler actively mutates the object's `__vptr` during construction and destruction:

```
[ Step 1: Memory Allocated for Derived (e.g., 32 Bytes on heap) ]
     |
     v
[ Step 2: Base::Base() begins ]
     |  Compiler emits: mov QWORD PTR [rdi], OFFSET Base::vtable
     |  --> `__vptr` points to Base::VTable!
     |  --> Any virtual call resolves to Base::virtual_func()!
     v
[ Step 3: Base::Base() finishes ]
     |
     v
[ Step 4: Derived::Derived() begins ]
     |  Compiler emits: mov QWORD PTR [rdi], OFFSET Derived::vtable
     |  --> `__vptr` is OVERWRITTEN to point to Derived::VTable!
     |  --> Virtual calls now resolve to Derived::virtual_func()!
```

During destruction, the reverse occurs:
1. `Derived::~Derived()` executes with `__vptr` pointing to `Derived::VTable`.
2. When `Base::~Base()` begins, the compiler resets `__vptr` back to `Base::VTable`.

#### 3. What Actually Happens When a Virtual Function is Called in a Constructor?

#### Scenario A: Defined Virtual Function Call
```cpp
class Base {
public:
    Base() { 
        log(); // Resolves to Base::log(), NOT Derived::log()!
    }
    virtual void log() { std::cout << "Base Initialized\n"; }
};

class Derived : public Base {
    std::string name_{"ProductionWorker"};
public:
    Derived() = default;
    void log() override { std::cout << "Derived: " << name_ << "\n"; }
};

Derived d; // PRINTS: "Base Initialized" (Derived::log is completely ignored!)
```

#### Scenario B: Indirect Pure Virtual Function Call (The `__cxa_pure_virtual` Crash)
If a base constructor calls a pure virtual function (`virtual void f() = 0;`), what happens?
- **Direct Call (`f()` in `Base::Base()`)**: The compiler catches this at compile-time and emits a compilation error.
- **Indirect Call (via a helper method)**: The compiler cannot catch this at compile-time:

```cpp
class Base {
public:
    Base() { 
        init(); // Calls helper
    }
    void init() {
        process(); // Calling pure virtual function while __vptr points to Base::VTable!
    }
    virtual void process() = 0;
};

class Derived : public Base {
public:
    void process() override { /* ... */ }
};

Derived d; // RUNTIME CRASH!
```

**The Crash Mechanics**:
1. During `Base::Base()`, `__vptr` points to `Base::VTable`.
2. Because `Base::process()` is pure virtual, `Base::VTable` puts a pointer to the standard runtime handler: **`__cxa_pure_virtual`** (on GCC/Clang) or **`_purecall`** (on MSVC).
3. When `process()` is called, the CPU jumps to `__cxa_pure_virtual`.
4. The handler prints `pure virtual method called` to `stderr` and immediately calls **`std::terminate()`**, aborting the program!

---

#### 4. Comparison with Other Languages (Java / C# vs C++)
- **Java and C#**: Virtual calls in constructors **do dispatch dynamically** to the derived override. In Java/C#, this is widely recognized as a major design trap because the derived override executes while derived fields are still `null` or default-zero.
- **C++**: Eliminates this trap by tying dynamic dispatch strictly to the lifetime phase of the object.

---

#### 5. Recommended Production Idiom: Two-Phase Initialization
If you need polymorphic behavior during object initialization, use a **Two-Phase Initialization** pattern with a static factory method:

```cpp
class Service {
protected:
    Service() = default; // Protected constructor
    virtual void post_construct() {} // Customization hook

public:
    virtual ~Service() = default;

    template <typename Derived, typename... Args>
    static std::shared_ptr<Derived> create(Args&&... args) {
        auto obj = std::make_shared<Derived>(std::forward<Args>(args)...);
        obj->post_construct(); // Safe: Object is fully constructed -> Dynamic dispatch works!
        return obj;
    }
};
```

### 3.2 The Mandatory Virtual Destructor Rule
If a class contains at least one `virtual` function, its destructor **must be declared `virtual`**!
Deleting a derived object through a base pointer without a virtual destructor results in **Undefined Behavior (C++ [expr.delete])**:

```cpp
class Base {
public:
    ~Base() { /* Non-virtual! */ }
};

class Derived : public Base {
    int* buffer;
public:
    Derived() : buffer(new int[1000]) {}
    ~Derived() { delete[] buffer; }
};

Base* p = new Derived();
delete p; // FATAL BUG: Calls ~Base() but SKIPS ~Derived()! Leaks 1000 ints + UB!
```

### 3.3 Object Slicing
Occurs when a derived object is assigned to a base object by value:

```cpp
Derived d;
Base b = d; // SLICING: Copies only the Base subobject! 
            // All Derived members are stripped, and b's vptr points to Base!
```

## 4. Static vs Dynamic Polymorphism: CRTP vs VTables

| Feature | Dynamic Polymorphism (VTables) | Static Polymorphism (CRTP) |
|---|---|---|
| **Dispatch Mechanism** | Runtime indirect pointer lookup via VTable. | Compile-time static function binding (`static_cast<Derived*>(this)`). |
| **Runtime Overhead** | 8B VPtr per object + indirect branch + cache misses. | **Zero overhead** (identical to direct function calls). |
| **Inlining** | Extremely difficult / blocked. | **Fully inlined by compiler**. |
| **Heterogeneous Collections** | Supported directly (`std::vector<std::unique_ptr<Base>>`). | Not supported directly (requires `std::variant` or type erasure). |

### The CRTP (Curiously Recurring Template Pattern) Implementation:
```cpp
template <typename Derived>
class BaseCRTP {
public:
    void execute() {
        // Compile-time static dispatch: Inlined!
        static_cast<Derived*>(this)->impl();
    }
};

class FastWorker : public BaseCRTP<FastWorker> {
public:
    void impl() { /* Inlined execution with zero virtual overhead */ }
};
```
